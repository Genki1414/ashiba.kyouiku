# 修了証の発行申請と、討議の候補日

## なぜ要るか

学科だけで修了する講座（足場の特別教育）は、確認問題と修了試験に受かった時点で
**もう修了している**。だから、その場で修了証を出してよい。

ところが、学科のあとに何かが残る講座で同じことをすると、
**まだ修了していない人に修了証が出る**。

職長・安全衛生責任者教育には45分の討議がある。討議はオンラインの同時双方向でやる
決めなので（docs/17）、いつやるかを決めないと先へ進めない。

そこで、学科を終えた人に**発行申請**を出してもらい、**こちらが候補日を返す**形にした。

> 討議の回を先に立てておく作りにはしない。
> 立てるまで誰も申し込めず、誰が待っているのかも分からない。
> **申請が来てから日を出す。**

## 講座ごとの関門

`src/content/courses.ts` の `gate` で決める。

| gate | 何が残るか | 候補日 | いまの講座 |
| --- | --- | --- | --- |
| （無し） | 何も。学科だけで修了 | — | 足場の組立て等特別教育 |
| `talk` | 討議。こちらが行う | **こちらが出す** | 職長・安全衛生責任者教育 |
| `drill` | 実技。事業者が自社で行う | 出さない（日を決めるのはこちらではない） | まだ無し |

`type` が `ondemand` でない講座（討議のある講座）には、必ず `gate` を付けること。
付け忘れると討議が済んでいない人に修了証が出る。`npm run test:issue` が見ている。

## 流れ（討議のある講座）

```
受講する人                         本部（運営）
─────────                         ────────
学科の全単元＋修了試験
      │
      ├─ 発行申請を出す ──────────→ 「発行申請」に出る（返事待ちが上）
      │   ・都合の悪い曜日を書ける      │
      │                               ├─ 候補日を出す（5件まで・2日より先）
      │                               │
      ←─ 候補日が届く ────────────────┘
      │
      ├─ 都合のよい日を選ぶ
      │   → 討議の回ができて、申し込みまで済む
      │
      ├─ その日に討議へ（/edu/…/talk）
      │   45分・課題への回答・講師の確認
      │
      └─ 修了証が出せるようになる
```

**同じ日を何人かに出したときは、その全員が同じ回に入る。**
別々の部屋に分かれると討議にならない。1回15人まで（`TALK_MAX`）。

こちらの都合が変わったら、日が決まったあとでも候補日を出し直せる。
そのとき、前の回の申し込みは自動で外れる。誰も居なくなった回は閉じる。

## 状態

| status | 意味 | 本人が次にやること |
| --- | --- | --- |
| （無し） | まだ申請していない | 申請を出す |
| `open` | 申請が出ている | 待つ |
| `offered` | 候補日を出した | 都合のよい日を選ぶ |
| `picked` | 日が決まった | その日に討議へ |
| `cleared` | 関門を通った | 修了証を出せる |
| `declined` | 断った（理由付き） | 直して出し直す |

`cleared` 以外では、修了証は出ない（`src/lib/cert.ts` の `eligible`）。

討議が済んだかどうかは、修了証の画面を開いたときに判定して、
条件を満たしていれば自動で `cleared` にする。
本部がボタンを押すまで修了にならない作りにすると、押し忘れた人が
いつまでも修了できない。**講師の確認は、討議の判定（`judgeTalk`）の中で見ている。**

## 決めたこと（変えるときは、理由も一緒に）

- **候補日を出すのは本部だけ。** 受講する人には作らせない。
  作らせると、講師の都合と関係なく日が入る。
  `/api/issue`（受講する人の側）からは `offer_slots` も `clear_request` も呼べない。
- **申請から作った回は、みんなの申し込み一覧に出さない**（`live_sessions.by_request`）。
  0022 は「`company_id` が空＝誰でも申し込める回」という作りなので、
  そのまま入れると、一人で受けている人の討議が全員の一覧に出て、
  よその人が申し込めてしまう。本人には、申し込みの行から引いて出す（`mySessions`）。
- **候補日の秒より下は捨てる**（`date_trunc('minute', …)`）。
  同じ日を2人に出したとき、秒がずれていると同じ回に集まらない。
- **申請の表に insert / update のポリシーを置かない。**
  状態を進めるのは `security definer` の関数だけ（service_role のみ実行可）。
- **1受講につき1件。** 出し直しは同じ行を使い回す。
  履歴を増やすと、いまどの状態なのかが読めなくなる。
- **日が決まったあとは、本人からは出し直せない。** こちらが出し直す。
- **修了したあとは触らせない。** 修了を取り消すことになる。
- **断るときは理由が要る。** 理由はそのまま本人に届く。

## 確かめ方

| | 何を見るか |
| --- | --- |
| `npm run test:issue` | 決まりそのもの（申請できる条件・状態ごとの案内・候補日の検査・一覧の並び） |
| `npx tsx tests/admin-db.mts` | 本物のスキーマに当てる（申請→候補日→選ぶ→通す、出し直し、よその申請を選べないこと） |
| `npm run test:e2e:issue` | 画面が状態どおりに出るか。7つの状態を通す |
| `npm run test:apishape` | 受講する人の側から候補日を作れないこと、書き込みのポリシーが無いこと |

`tests/admin-db.mts` の動かし方は `tests/README.md` を見ること。

## 講座を公開するときの手順

1. `src/content/courses.ts` を `ready: true` にする
2. `npm run build:sql`（**lessons が入るのはここ**。準備中の講座の単元は入らない）
3. `supabase/apply-all.sql` を Supabase の SQL Editor で流す（版は 0023）
4. 値段を決める（`src/lib/pricing.ts` の `DEFAULT_COURSE_PRICE`、
   または Vercel の環境変数 `SEAT_UNIT_PRICE_◯◯`。どちらも税抜）
5. 討議に使う Zoom の部屋。
   日が決まった申請の行に「つなぎ先を入れる」が出るので、そこへ貼る。
   https のみ。一覧には出ず、当日「入る」を押した人にだけ渡る。
   **入れておかないと、当日「入る」を押しても部屋が渡らない。**
   本部の画面には「つなぎ先：まだです」と黄色で出る
6. 事業者印の画像を `public/` に置く。
   名前は `seal`、拡張子は png / jpg / jpeg / webp のどれでもよい
   （`SEAL_SRCS` の順に探す）。**iPhone の HEIC は不可**。
   ブラウザによって出ないので、修了証から印だけ消える。

   置かなければ、社名から角印を描く（`drawKakuin`）。
   縦書きで右の列から左へ、朱色。印を押さなくても名義の入った紙が出る。

   白い紙に押した印を写真で撮ったものでよい。
   台紙が生成りなので白い四角が出そうだが、貼る前に紙を抜いている
   （`knockOutPaper`）。自分で背景を抜いた png は、そのまま使う
