# ホームのお知らせ（本部からの返事）

## なぜ要るか

こちらが手を動かしても、**相手には何も伝わらない。**

| こちらがやること | 相手はどうなるか |
| --- | --- |
| 参加申込を許可した | 開いてみるまで分からない |
| 入金を確認して受講コードを出した | 担当者は、開いてみるまで分からない |
| 討議の候補日を出した | 待っている本人に届かない |
| 討議の入り口が決まった | 当日まで分からない |
| 断った | **理由がどこにも出ない** |

待っている側にできるのは、何度も開き直すことだけ。
そして**開くのをやめた人には、こちらが動いたことが永久に伝わらない。**

参加申込の許可はとくに効く。許可を出すまでその人の教材は開かないので、
許可したことが伝わらないと、待っている本人は「まだ駄目なのか」と思ったまま止まる。

申込が来たことは LINE で運営に届くようにした（docs/22）。
**その逆向きが、これ。**

## 決めたこと

### 住所はしまわない

行に入れるのは、**種類（kind）と講座**だけ。
「どこを開くか」は種類から組み立てる（`src/lib/noticeText.ts`）。

- 画面の場所を1つ動かしただけで、過ぎた行が全部どこにも行かない行になる。
  組み立てにしておけば、直すのは1か所
- しまった住所へ飛ばす作りは、どこかで外から入れられる道になる。
  作らなければ、その話が起きない

### 画面からは書けない

`notices` に insert / update のポリシーを置いていない。
書けるのは `add_notice`（service_role だけ）。

置くと、**自分あてに好きな知らせを作れる。**
「会社とつながりました」を自分で書いて、担当者に見せることができてしまう。
`supabase/tests/notices.sql` の⑫が見ている。

### 読めるのは本人だけ

担当者にも本部にも見せない。宛てた本人への返事であって、名簿ではない。

### 断るときは、理由も返す

`note` に入れて、そのまま画面に出す。
理由の無い「断られました」は、受け取った人が次に何をすればいいか分からない。

**HTML としては流し込まない**（`dangerouslySetInnerHTML` を使わない）。
書いた字がそのまま画面の作りになる。

### 開いたら全部を読んだことにする

1件ずつ押させると、押し忘れた1件で丸い数字が消えなくなる。
**消えない数字は、そのうち見られなくなる。**

ただし、**その場では数字も黄色い点も消さない。**
未読があると開いた形で出すので、消してしまうと
「2件」も点も一瞬で消えて、**届いた回に限って、どれが新しいのか分からない。**
覚えるのはサーバだけにして、画面は次に開いたときに変わる。

### 押し直しを1行にまとめる

**60秒のあいだの、同じ宛先・同じ種類・同じ講座は1行**にする
（一言は新しいほうで上書きし、未読に戻す）。

押し間違いの押し直しは日常にある。そのたび増えると読めなくなる。
60秒より前の同じ返事は、別の出来事として並べる。

### 残せなくても、返事は通す

知らせが書けないから許可が出せない、では本末転倒。
`addNotice` は失敗しても例外を投げないし、呼ぶ側は返り値で分岐しない。

### 古いものは捨てる

知らせは記録ではない。読んだあとの1年前の「許可されました」に用は無い。
受けた記録そのものは `enrollments` と `certificates` に残る（docs/16 の3年保存）。

`sweep_notices(180)` で捨てられる。いまは手で流す。

## いま知らせている所

| 種類 | どこから | 誰に | 開く場所 |
| --- | --- | --- | --- |
| `member_ok` | `/api/admin/member`（許可） | 申し込んだ人 | `/` |
| `member_ng` | `/api/admin/member`（断る） | 申し込んだ人 | `/me` |
| `cert` | `/api/admin/cert`（発行） | 受けた人 | `/edu/{講座}/cert` |
| `seat` | `/api/owner/orders`（入金確認） | 申し込んだ担当者 | `/admin` |
| `train` | `/api/owner/orders`・`/api/owner/training` | 本人 | `/training` |
| `slot` | `/api/owner/issue`（候補日） | 申請した人 | `/edu/{講座}/cert` |
| `room` | `/api/owner/issue`（部屋） | 申請した人 | `/edu/{講座}/talk` |
| `pass` | `/api/owner/issue`（通した） | 申請した人 | `/edu/{講座}/cert` |
| `issue_ng` | `/api/owner/issue`（断る） | 申請した人 | `/edu/{講座}/cert` |

**宛先は「待っていた人」。押した人ではない。**
入れ違えると、押した本人に「許可されました」が出る。

**こちらが手を動かして、相手が待っていることが動いたら、全部ここに入れること。**
1つでも抜けると、そこだけ伝わらない。`npm run test:notice` が数を見ている。

### 出さないことにした所

- **修了証の取り消し・実務トレーニングの取り消し。**
  こちらから一言あるべき話なので、知らせだけが先に届くほうが困る
- **カード払いが通ったとき。** 払った本人はその場に居る。
  本部の返事ではないので、ここには入れない

## 確かめ方

```sh
npm run test:notice        # 画面と繋ぎ込みの決まり
```

SQL の分（押し直しの窓、読んだ印の届く範囲、作れる人）は
`supabase/tests/notices.sql`。流し方は `supabase/tests/README.md`。

画面は、参加申込を1件出して、別の窓で許可する。
許可したほうではなく、**申し込んだほうのホーム**に出れば通っている。

## これから

**Push（スマホに出る通知）は、この上に載せる。**

Push には**本文を載せない。**「1件増えた」と叩くだけにして、
中身はここから読みに来させる。

- 通知はロック画面に出る。断った理由や講座の名前がそこに出る
- 本文を載せると、こちらで暗号をかける手間が増える（RFC 8291）。
  載せなければ、その話が起きない

**iPhone は、ホーム画面に追加していないと Push が届かない。**
だから「はじめかた」に追加のやり方を入れてある（`src/lib/pwa.ts`）。
